# CyberClubManager — Система управления киберспортивным клубом

## Описание проекта
Программный комплекс предназначен для автоматизации бизнес-процессов современного компьютерного клуба. Система обеспечивает учет аренды игровых мест, автоматизирует проведение внутренних турниров и контролирует продажи сопутствующих товаров через внутренний магазин с автоматическим списанием со склада.

---

## Команда разработки и распределение бизнес-задач

Проект разработан командой из 3-х человек (или распределен внутри мини-команды) с четким разделением зон ответственности:

1. **Разработчик 1 (Тимлид / Artur Stepanyan)** * **Бизнес-задача:** Модуль бронирования и учета аренды игровых мест (обычные ПК и VIP-зоны) с контролем игровых сессий.
   * **Паттерн:** Порождающий — `Factory Method` (Фабричный метод).
   * **Ветка в Git:** `feature/pc-booking`

2. **Разработчик 2**
   * **Бизнес-задача:** Модуль управления турнирными сетками, регистрация команд и автоматическое распределение пар игроков.
   * **Паттерн:** Структурный — `Facade` (Фасад).
   * **Ветка в Git:** `feature/tournament-management`

3. **Разработчик 3**
   * **Бизнес-задача:** Модуль внутриклубного магазина (мерч, девайсы, напитки) со складским учетом и генерацией чеков.
   * **Паттерн:** Поведенческий — `Observer` (Наблюдатель).
   * **Ветка в Git:** `feature/shop-warehouse`

## Архитектурные паттерны и стандарты

### 1. Архитектура MVC (Model-View-Controller)
Проект строго разделен на три слоя для изоляции логики от представления:
* **Model:** Хранит состояние (ПК, Турниры, Товары) и не знает о существовании консоли.
* **View:** Отвечает исключительно за красивый вывод информации в консоль и считывание строк от пользователя.
* **Controller:** Перехватывает ввод пользователя из `View`, вызывает методы бизнес-логики из `Model` и обновляет `View`.

### 2. Паттерны проектирования
* **Factory Method (Порождающий):** Используется при создании игровых мест. Позволяет прозрачно генерировать стандартные места (StandardPC) и премиальные места (VipPC) с разными коэффициентами стоимости и набором девайсов без завязки на конкретные классы.
* **Facade (Структурный):** Предоставляет единый упрощенный интерфейс `TournamentFacade` для создания турнира, регистрации команд и генерации сетки одним вызовом, скрывая сложную внутреннюю координацию подсистем.
* **Observer (Поведенческий):** Реализует систему уведомлений. Администрация клуба и складские модули подписываются на изменения остатков товаров. При критическом снижении позиций на складе срабатывает автоматическое оповещение.

### 3. Хранение данных (Текстовая БД)
Все данные персистентны и сохраняются в структурированные текстовые файлы (`.txt` / `.csv` формат). Запись и чтение происходят через слой репозиториев (`Repositories`), гарантируя сохранение данных между перезапусками приложения.

### 4. Качество кода и тестирование
* Проект покрыт Unit-тестами на базе фреймворков **NUnit** и **Moq**.
* Все методы задокументированы с использованием XML-комментариев (`///`).
* Код проверяется статическим анализатором на соответствие стандартам `StyleCop`.

## Правила работы с репозиторием (GitHub Flow)

Проект использует упрощенную и чистую модель ветвления GitHub Flow:

1. Разработка ведется строго в ветках бизнес-задач (`feature/pc-booking`, `feature/tournament-management`, `feature/shop-warehouse`), созданных от ветки `development` или `main`.
2. После выполнения своей задачи разработчик создает **Pull Request (PR)** в ветку `development`.
3. **Тимлид** проводит код-ревью, проверяет прохождение тестов и отсутствие ворнингов StyleCop.
4. После одобрения PR происходит слияние (`Merge`). Слияние напрямую в основные ветки минуя PR строго запрещено.

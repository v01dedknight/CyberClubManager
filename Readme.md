# CyberClubManager - Система управления киберспортивным клубом

## Описание проекта
Программный комплекс предназначен для автоматизации бизнес-процессов современного компьютерного клуба. Система обеспечивает учет и бронирование игровых мест, гибкое управление аппаратными конфигурациями компьютеров по залам, а также автоматический контроль времени игровых сессий с системой лояльности и уведомлений.

---

## Команда разработки и распределение бизнес-задач

Проект разработан командой из 3-х человек с четким разделением зон ответственности и строгим соблюдением гит-флоу:

1. **Тимлид (Artur Stepanyan)**
   * **Бизнес-задача:** Модуль бронирования и учета аренды игровых мест (обычные ПК и VIP-зоны) с контролем игровых сессий.
   * **Паттерн:** Порождающий - *Factory Method (Фабричный метод)*.
   * **Стабильная ветка в Git:** `feature_booking-management`

2. **Разработчик (Никита Черненко)**
   * **Бизнес-задача:** Модуль управления конфигурациями ПК (добавление девайсов, системных характеристик и разделение компьютеров по игровым залам: VIP/Общий).
   * **Паттерн:** Структурный - *Composite (Компоновщик)*.
   * **Стабильная ветка в Git:** `feature_computer-management`

3. **Разработчик (Екатерина Бобкова)**
   * **Бизнес-задача:** Модуль уведомлений и системы лояльности (отслеживание оставшегося времени сессий, автоматические алерты в консоль администратора и расчет тарифов/скидок).
   * **Паттерн:** Поведенческий - *Observer (Наблюдатель)*.
   * **Стабильная ветка в Git:** `feature_loyalty-notifications`

## Архитектурные паттерны и стандарты

### 1. Архитектура MVC (Model-View-Controller)
Проект строго разделен на три слоя для изоляции логики от представления:
* **Model:** Хранит состояние системы (ПК, бронирования, пользователи), содержит бизнес-логику и полностью изолирован от консольного ввода/вывода.
* **View:** Отвечает исключительно за вывод информации в консоль и считывание строк от пользователя.
* **Controller:** Перехватывает ввод пользователя из View, вызывает соответствующие методы бизнес-логики из Model и обновляет View.

### 2. Паттерны проектирования
* **Factory Method (Порождающий):** Используется при создании игровых мест. Позволяет прозрачно генерировать стандартные места (`StandardPC`) и премиальные места (`VipPC`) с разными коэффициентами стоимости и набором девайсов без завязки на конкретные классы.
* **Composite (Структурный):** Применяется для управления структурой клуба. Объединяет отдельные компьютеры в группы (игровые залы), позволяя взаимодействовать с целым залом (например, проверить доступность или применить групповую конфигурацию) так же легко, как с одиночным ПК.
* **Observer (Поведенческий):** Реализует систему умных уведомлений. Модуль отслеживания сессий выступает в роли субъекта, а консоль администратора - в роли наблюдателя. При истечении времени сессии пользователя система автоматически генерирует и отправляет уведомление.

### 3. Хранение данных (Текстовая БД)
Все данные персистентны и сохраняются в структурированные текстовые файлы (`.txt` / `.csv` формат). Запись и чтение происходят через слой репозиториев (Repositories), гарантируя сохранение данных между перезапусками приложения.

### 4. Качество кода и тестирование
* Проект покрыт Unit-тестами на базе фреймворков **NUnit** и **Moq**.
* Все методы и интерфейсы задокументированы с использованием **XML-комментариев** (`///`).
* Код проверяется статическим анализатором на соответствие стандартам **StyleCop** (включая строгое отслеживание правил SA1312, SA1516, SA1505, SA1518).

## Правила работы с репозиторием (Git Flow)

В проекте используется регламентированная модель ветвления, защищенная правилами GitHub Branch Protection:

1. **Ветка master** - ветка для хранения стабильного кода. Мердж выполняется Тимлидом без пулл-реквеста напрямую через консоль.
2. **Ветки feature_*** - ветки для хранения стабильного кода конкретной бизнес-задачи (`feature_booking-management`, `feature_computer-management`, `feature_loyalty-notifications`). Доступ к прямому пушу заблокирован. Попадание кода сюда возможно **строго через Pull Request и код-ревью Тимлида**.
3. **Ветки wip-feature_*** - персональные рабочие ветки разработчиков для хранения промежуточных процессов разработки (формат: `фамилия.имя_wip-feature_название-модуля`). Здесь ведется вся основная работа.

*Примечание: Пулл-реквесты с нарушением правил нейминга или ворнингами статического анализатора отклоняются автоматически без ревью кода.*
